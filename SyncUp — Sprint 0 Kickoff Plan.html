4. How the 2 Groups Work in Parallel

The trick: Group 1 never waits on Group 2's real backend. Once the contract is frozen (Day 2), Group 1 builds against a mock of it, and Group 2 builds the real thing behind that same contract. They only need to sync when the contract changes or at planned merge points.
StepGroup 1 doesGroup 2 does
Day 2 — Contract freezeReviews & agrees on REST endpoints + socket event names/payloadsAuthors the contract (endpoints, socket events, DB shape) and shares it as a shared types/ package or OpenAPI/JSON schema doc
Day 3Builds UI against a mock server (MSW, json-server, or a fake Socket.io emitter) that returns contract-shaped fake dataBuilds the real API, DB, and Socket.io server behind the same contract
Day 4 — MergeSwaps mock base URL / socket URL for Group 2's real, running serviceExposes a stable local/staging endpoint for Group 1 to point at
OngoingAny UI need for a new field/event → proposes a contract changeApproves contract change, updates shared types, implements it
Practical setup:
  • Put shared TypeScript types/interfaces in packages/types/ in the monorepo — both groups import from the same source, so a contract change is a single PR both sides can see.
  • Group 1 stubs the backend with Mock Service Worker for REST and a tiny fake emitter for socket events — this is what removes the daily dependency on Group 2 being "done".
  • Schedule a 15-min daily sync + a longer merge session on Day 4 and end of each sprint — that's the "meet to merge" checkpoint, not a constant back-and-forth.

Note on 2-group split: Group 1 now owns pure UI — rendering, layout, and client state, including the chat and call interfaces, but not the networking underneath them. Group 2 owns everything that moves or stores data: the database, auth, WebSocket server, WebRTC signaling, caching, and infra. The hand-off point is a set of socket events and REST endpoints Group 2 exposes and Group 1 consumes — define that contract on Day 1 so neither group blocks the other.

6. Learning Path — Alongside the Work

Module A · Group 1Frontend UI & State
  • CSS Grid/Flexbox for adaptive dashboards — build The Hub layout as practice
  • Global state: pick one of Context API / Redux Toolkit / Zustand and learn it deeply rather than sampling all three
  • List virtualization (react-window or react-virtual) — needed before Live Chat history gets long
  • Optimistic UI patterns — study how apps like Linear/Trello roll back failed updates
Module B · Group 2Real-Time & Concurrency (your focus)
  • WebSocket protocol basics — handshake, frames, heartbeat/ping-pong
  • Socket.io rooms & namespaces for per-squad channels, and how to design the chat event contract Group 1's UI will consume
  • WebRTC fundamentals: ICE, STUN vs TURN, SDP offer/answer flow, signaling server design
  • Reconnection strategies — exponential backoff, session resumption, presence tracking in Redis
Module C · Group 2Media & Cloud Infra
  • S3/GCS pre-signed URLs — direct browser-to-cloud upload pattern
  • FFmpeg basics: transcoding formats/bitrates for stored recordings
  • Docker fundamentals — multi-stage builds, container networking
  • Background job processing (BullMQ or a Kafka consumer worker)
Module D · Group 2Databases & Distributed Design
  • Relational schema design — normalize Users/Squads/Tasks with proper FKs
  • ACID transactions & row-level locking to prevent race conditions
  • Redis data structures (hash, sorted sets) for presence & caching
  • Event-driven basics: Kafka/RabbitMQ producer-consumer model
